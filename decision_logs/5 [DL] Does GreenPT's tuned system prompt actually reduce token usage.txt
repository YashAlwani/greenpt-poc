[DL] Does GreenPT's tuned system prompt actually reduce token usage?
GreenPT POC


1. Context

Project: GreenPT benchmarking POC / day 2 (first full run, reading the numbers).

Why this matters right now:
The assumption going in was that GreenPT's tuned system prompt on green-l would natively bias the
model toward lean JSON — that's the entire "prompt_engineering" optimization layer. The first full
run punctured that. green-l with no extra instruction sends 15.0% MORE tokens than green-l-raw
with a vanilla "Return ONLY valid JSON" system prompt — across all 48 rows. Quality is identical.
This breaks the pitch for the prompt_engineering method specifically and forces a smart-routing
rule change in DL-05 before the SDK ships.

Where this fits:
Falsifies the assumption baked into smart_route v0 (DL-05). Feeds directly into the report
(DL-07) and into the product follow-up memo for the GreenPT team.

2. Research question

Does GreenPT's tuned system prompt on green-l (compared to green-l-raw with a vanilla extraction
prompt) actually produce shorter JSON outputs?


3. Current LO stage

[x] Realizing  — ran the full 192-row benchmark
[x] Managing   — read the results, found the assumption was wrong, logged it as a finding


4. What makes this a valid falsification

- Pattern holds across all 48 rows x 4 use cases (n is big enough)
- Quality is preserved — if green-l were trading verbosity for higher quality, that's a
  different story; here it's spending more tokens for nothing
- The savings math (DL-02) is correct — cross-method denominator, baseline always 0%


5. What I decided

Treat this as a confirmed finding. Log it. Use it to disable prompt_engineering as a smart-
routing default (DL-05 -> v1). Communicate it to the GreenPT product team as a system-prompt
tuning opportunity.


6. Why this decision

Method: Lab (controlled comparison across the full 48-row dataset).

The pattern is unambiguous. Across all 48 rows x 4 methods, prompt_engineering (green-l with
no extra system prompt) transmitted on average 15.0% MORE tokens than baseline (green-l-raw +
vanilla "Return ONLY valid JSON" system prompt).

Per use case (@outputs/results.csv -> token_savings_pct, method=prompt_engineering):

  intent_classification   -43.5%   (sends 1.44x as many tokens as baseline)
  invoice_parsing          -0.4%
  resume_parsing           +0.2%
  summarization            +3.7%

Mean G-Eval score was identical to baseline (3.14 / 3.14) — quality wasn't traded for verbosity,
just verbosity for nothing.

[IMAGE: outputs/chart_savings.png — Bar chart of mean token savings by method. prompt_engineering
is the only bar extending left of zero. That chart is the clearest single image in the benchmark
output for showing that prompt_engineering is strictly worse than doing nothing.]

The most likely explanation: green-l's baked-in system prompt is tuned for quality (Dutch grammar
guardrails, multilingual writing assistance per the model card), not for token compression. With
no explicit instruction to be terse, the model defaults to a more elaborate output style than
green-l-raw on a vanilla extraction prompt.

This is not a bug in GreenPT. The GreenPT team made a deliberate design choice to prioritize
quality assistance in the tuned prompt. The finding is that "prompt_engineering" as a standalone
optimization layer is not a token-saving strategy on this product — you need to either stack it
with client-side TOON (combined, which adds an explicit terse instruction) or skip it entirely.

What I'd recommend:
Three things, in order of effort.

  1. Smart routing: prompt_engineering should never be the default for any use case. Always
     prefer combined (which adds the terse instruction) or postprocess (client-side compression
     only). One-line change in sdk.smart_route (@sdk.py).
  2. Product follow-up: surface this to GreenPT — they can add a "be terse" line to the green-l
     system prompt, which would make prompt_engineering net-positive without changing the quality
     story.
  3. Report framing: do not promise that prompt_engineering alone saves tokens. Lead with
     combined or postprocess in any client deck.

GAP found:
We measured token counts, not character counts on the wire. If GreenPT's billing uses their own
tokenizer (not tiktoken cl100k_base), the direction of the result might shift by a few percent.
Worth confirming with the GreenPT pricing team before any public claim about "green-l sends more
tokens." Direction is robust across hundreds of rows and both small and large use cases, so the
shift would have to be systematic to change the conclusion.


7. Does this hold up

- Pattern holds across the dataset:  ✅ -15.0% mean, with all four use cases in
                                         negative or near-zero territory; no use
                                         case where prompt_engineering is positive
                                         by more than noise
- Quality preserved:                 ✅ 3.14 mean G-Eval, identical to baseline
- Savings math correct:              |  baseline_tokens column in results.csv lets
                                         anyone verify a row by hand — but tiktoken
                                         cl100k_base is a proxy for Mistral's actual
                                         BPE tokenizer. Exact percentages could shift
                                         by a few points. Direction is robust.

❌ Original assumption ("tuned system prompt = lean output") — falsified by 192 data points.

Assumptions I'm making:
The token deltas are real, not artifacts of tiktoken being wrong on Mistral. Confidence is high
because the pattern holds across hundreds of rows; tiktoken miscount would be more random.
intent_classification's -43.5% is an average across 12 rows, not a single-row outlier.

What surprised me:
Quality was identical. I expected green-l to be slightly higher quality at the cost of more
tokens — that would at least make the trade-off honest. Instead the model spends more tokens
producing the same answer. That's strictly worse from a token economics standpoint and is the
single most actionable finding from this run.


8. What this unlocks

What I can now do:
Codify "never default to prompt_engineering" as a routing rule. Frame the report around combined

Ongoing monitoring:
Re-run the same 48-row benchmark whenever GreenPT updates green-l's system prompt
(@outputs/results.csv is the regression baseline). The -15.0% number is a regression test for

landed.

How I'll know this worked:
After GreenPT adds a terse instruction to green-l's system prompt, the same benchmark should
swing prompt_engineering from -15.0% to net positive. That delta is the observable signal that
the finding was acted on.

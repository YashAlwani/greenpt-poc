Finding 1 — prompt_engineering loses across the board:

This was the assumption going in: GreenPT's tuned system prompt on green-l would
natively produce shorter outputs than a vanilla extraction prompt. The data broke it.
Across all 48 rows, prompt_engineering transmitted 15.0% MORE tokens than baseline
at identical G-Eval quality (3.14 / 3.14) — spending more tokens for nothing.

Per use case (@outputs/results.csv, column token_savings_pct, filter
method=prompt_engineering):

  intent_classification   -43.5%
  invoice_parsing          -0.4%
  resume_parsing           +0.2%
  summarization            +3.7%

The most likely mechanism: green-l's system prompt is tuned for quality — Dutch
grammar guardrails, multilingual assistance — not terseness. With no explicit
instruction to be compact, green-l defaults to a more elaborate output style than
green-l-raw on a vanilla "Return ONLY valid JSON" prompt. Quality is identical;
verbosity is free, so the model uses it. The GreenPT team made a deliberate design
choice. The finding is just that prompt_engineering alone is not a token-saving
strategy on this product. Full DL: @decision_logs/03_finding_prompt_engineering_verbose.txt

Finding 2 — combined is the quality champion, not the universal savings winner:

The simplest pitch for combined was "stacks both layers, has to win everywhere."
The full run broke that too. Combined's mean savings (+2.0%) is dragged down by two
losing use cases. The mechanism is mechanical — the combined method prepends a TOON
instruction block to every user message (@tools/greentpt_tools.py:45-56, the
_toon_user_prefix constant). That block is approximately 80 tokens of fixed overhead.

For invoice_parsing, the ~80-token overhead lands on top of a ~150-token compressed
output from a 12-field nested schema with line-item arrays. Net: +32.2%.

For intent_classification, the ~80-token overhead lands on top of a ~30-token
baseline output ({"intent": "...", "confidence": 0.0}). The overhead exceeds the
entire output. Net: -36.0%.

The 68 percentage-point spread between those two cells — across 12 rows each — is
not noise. Full DL: @decision_logs/04_finding_combined_overhead_tiny_outputs.txt

postprocess — the quiet winner:

Going in, combined was the expected dominant method. postprocess was the fallback.
What the data actually shows: postprocess delivers +5.6% savings across every use
case with zero quality cost (3.21 / 3.21 vs baseline). No routing logic needed.
No schema-size check. Just consistently wins, or breaks even, everywhere. It's not
the exciting method — no single +32.2% headline — but it's the only method with
no losing use case and no quality trade-off.

Failure tally:

  status=ok              176 rows
  status=parse_failed     16 rows  (LLM returned non-JSON)
  status=decode_failed     0 rows
  status=api_failed        0 rows
  quality_warning=True     6 rows  (G-Eval < 3, kept in averages)

Zero pipeline crashes across 192 rows. The failure taxonomy from DL-00 held — every
failure was tagged with a status code rather than silently dropped. The 16
parse_failed rows are visible in @outputs/results.csv and kept in the aggregate with
savings_pct=0 by convention (DL-00 rule 6).

What I'd recommend:
Three things land out of this data.

  1. Honest framing: postprocess is the universal-savings winner; combined is the
     quality champion and multi-field savings winner; prompt_engineering is not a
     standalone path to savings. Lead with that nuance, not a single headline number.
  2. Smart routing v1: codify "postprocess for tiny outputs, combined for
     nested/multi-field schemas, never prompt_engineering as default" as a single-
     function update to sdk.smart_route (@sdk.py:31-55). The data now supports
     every branch.
  3. Product memo to GreenPT: the green-l verbosity finding is the most actionable
     result. A "be terse" instruction in green-l's system prompt would flip
     prompt_engineering from -15.0% to net-positive without touching the quality
     story. One line in the system prompt. The same 48-row re-run is the regression
     test for whether the change landed.

GAP found:
The reasoning tier (green-r) was not benchmarked. We don't know whether the patterns
above hold on the larger model — whether combined's instruction overhead is a
proportionally smaller cost at higher output quality, or whether prompt_engineering
turns positive once the model is more capable of following implicit brevity cues.
Same methodology, same 48 rows, ~10 minutes, ~0.10 EUR. That's the natural next run.


7. Does this hold up

- Fairness rules held:         ✅ same compute, T=0, max_tokens=1024 across
                                   all 192 rows (DL-00 rule 1, confirmed in
                                   @pipeline/graph.py:22-31)
- Cross-method savings math:   ✅ baseline always 0.0%; all other methods
                                   anchored to baseline_tokens per row (DL-02
                                   formula, @pipeline/graph.py:eval_node)
- n is big enough:             ✅ 12 rows per per-use-case cell; the
                                   68-point spread between invoice_parsing
                                   and intent_classification for combined
                                   is not noise
- Failures accounted for:      ✅ 16 parse_failed rows and 6 quality_warning
                                   rows visible and tagged separately in
                                   @outputs/results.csv; not silently averaged

Assumptions I'm making:
The 48-row dataset is representative of the workloads GreenPT's real customers will
run. Four canonical use cases at three sizes covers the main schema-shape space, but
a customer doing deeply nested financial document extraction might land in a different
regime than the invoice_parsing case here.

What surprised me:
postprocess being the consistent winner on savings. The expectation going in was that
combined — stacking both optimization layers — would dominate. What the data showed
instead was that combined has a floor problem: the fixed ~80-token instruction
overhead makes it net-negative on any schema where the baseline output is smaller
than the overhead. postprocess has no floor. It applies client-side key shortening
and minification without prepending anything — so it wins, or breaks even, on every
use case without a routing decision. That's the quiet headline of this benchmark.
It's the method that just works, while the more ambitious method needs a routing
layer to stop it from actively hurting.

How GreenPT works

    
GreenPT is a token-reduction proxy for LLM structured-output calls. It sits between your app and any OpenAI-compatible endpoint, transparently shrinking JSON responses before they hit your billing meter.


    


      

        
🗜

        
TOON — Token Optimization Object Notation

        
TOON is a lossless JSON compression scheme that shortens key names. Before each session a key map is negotiated:

        
{"invoice_number":"a","total_amount":"b",...}

        
The model returns {"a":"INV-001","b":7891.60}. Your client decodes it back to full names in microseconds. Because JSON keys repeat across millions of calls, cutting them once saves tokens on every single request.

      


      

        
🔀

        
Smart router

        
The auto method inspects your schema and picks the optimal strategy:

        
    
          
  • Tiny flat schema (≤ 2 short keys) → baseline — compression overhead isn't worth it.
    • 
          
  • Deep / array-heavy schema → combined — TOON wins on repetition.
    • 
          
  • Long key names → postprocess — key shortening is the main win.
    • 
          
  • Everything else → prompt_engineering.
    • 
        

      


      

        
baseline

        
green-l-raw + vanilla prompt

        
Calls green-l-raw with a standard extraction system prompt. No optimization. This is the reference point — token savings for all other methods are measured against this.

      


      

        
postprocess

        
green-l-raw + TOON (client-side)

        
Same baseline call, but the response is TOON-encoded after it arrives. The model never knows — the compression is invisible. Good when you can't change the model but still want wire savings.

      


      

        
prompt_engineering

        
green-l tuned model

        
Uses green-l, which has GreenPT's optimization system prompt baked in. The model is already primed to return compact output. No TOON, but the model's inherent verbosity is reduced.

      


      

        
combined

        
green-l + TOON (maximum compression)

        
Stacks both layers: the green-l tuned model plus TOON key-shortening instructions injected into the user message (green-l rejects system prompts — they're reserved for its built-in optimization). Maximum token reduction.

      


    


    

      
📦

        The key map is sent once per session as session-level metadata — not on every request. Only the compressed payload travels on each call.
      

    


    

      
📊

      
Measuring savings

      
Token counts use tiktoken cl100k_base on the raw model output (tokens_before) vs the on-wire compressed string (tokens_after).

      
savings % = (baseline_tokens − method_tokens) / baseline_tokens × 100

      
Baseline is always 0%. Negative savings mean the method transmitted more tokens than baseline for that call — typically schema-level overhead on very short responses.

      
Quality is scored 1–5 by a second LLM judge using G-Eval on the schema-validated decoded output.

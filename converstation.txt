Great reframe. This sharpens the whole problem significantly. Here's how to think about it:

The core constraint you're designing around
Your optimization pipeline touches only the JSON output structure — not the prompt, not the task, not the content. So the dataset needs to be designed to make that optimization measurable, comparable, and meaningful.

What actually matters when building the prompts
1. The output JSON must be the variable, not the input Every prompt should explicitly request JSON output. The input text is just the trigger — what you're really designing is the expected output schema. Size (S/M/L) should therefore be defined by output token complexity, not input length. Your earlier answer of input tokens (300–1000) is fine as a proxy, but the real signal is output token count — a 300-token input asking for a flat 2-field JSON is a very different benchmark than one asking for a nested 15-field schema.

2. Schema complexity needs to vary systematically You need variation across three dimensions in your schemas:

Depth — flat vs. nested objects
Breadth — number of fields
Field types — strings, arrays, numbers, booleans, nullable fields
These drive how much the optimizer can actually compress. A flat schema with 3 string fields has almost no room to optimize. A deeply nested schema with arrays of objects is where the real token savings show up.

3. Each use case has a natural optimization ceiling

Structured Data Extraction — schema is predictable, values are deterministic. Easy to measure quality degradation.
Text Analysis & Classification — small, flat outputs. Optimization gains will be minimal. This is your control case — it proves the optimizer knows when NOT to change much.
Content Generation with Metadata — large nested outputs, highest token savings potential, highest quality risk. This is your stress test.
4. You need a baseline token count per prompt Before any optimization runs, you need to know how many output tokens the raw (unoptimized) response uses. This means the dataset should include a baseline_output_tokens column, or the script needs to generate it on first run. Without this, you can't calculate savings %.

5. Prompts should NOT over-constrain the schema If your prompt says "return JSON with exactly these fields: name (string), date (string), amount (number)" — the optimizer has nothing to do. Prompts should ask for JSON output naturally, leaving the schema implicit, so the optimizer has room to act. Think: "Extract the key invoice details as JSON" not "Return a JSON with fields: invoice_id, date, vendor, amount".

6. Quality degradation needs to be detectable Since your reference output is schema-only, you need the schema to have enough fields that a bad optimization (dropping fields, wrong types, collapsing arrays) is actually catchable by G-Eval. A 2-field schema won't surface subtle quality loss.

Things you probably haven't considered yet
Nullable / optional fields — does the optimizer incorrectly drop them vs. correctly omit them? This is a major edge case.
Arrays of objects — the biggest token consumer, and the hardest to optimize without losing fidelity. You need these in L prompts.
Prompt phrasing consistency — if prompts are phrased differently per use case, you can't isolate whether token savings come from the schema or the prompt wording. Keep phrasing formulaic.
What "same prompt, 5 runs" actually tests — it tests LLM output variance, not optimizer variance. If the optimizer is deterministic, 5 runs tells you about the model's stability, not the optimization quality. Worth clarifying which variance you care about.
The no-op case — you need at least some prompts where optimization should produce zero savings (e.g. a single-field JSON). This proves the pipeline doesn't over-optimize.
Does this change how you're thinking about the generation script? The key shift is: design the output schemas first, then write prompts that naturally produce them.

Good question — this is an important design decision. There are two approaches:

Option A — Agent-prompted (LLM generates the data)
The script sends a structured prompt to Claude for each use_case × size combination, asking it to generate a realistic prompt + schema-only expected output. The script just orchestrates the calls and writes the CSV.

Pros:

Prompts feel natural and varied — no two rows read the same
Schemas reflect realistic LLM output shapes
Easy to scale up later (change n=3 to n=10)
The content stays fresh without manual effort
Cons:

Non-deterministic — running it twice gives different rows
You need to review the output before feeding it to the benchmark
Costs tokens to generate
Option B — Hardcoded
You write all 36 rows by hand in the script, or define fixed templates the script fills in.

Pros:

Fully reproducible — same output every run
No review step needed
Cons:

36 rows by hand is tedious and the prompts will feel samey
Hard to extend later
Defeats the purpose — you'd be manually doing what a script should do
The right answer for your use case
Option A, but with a hardcoded skeleton. Meaning:

The schemas are hardcoded per use case × size — you define them once, they don't drift
The prompt content is agent-generated — the LLM writes the invoice text, the resume body, the article to summarise, etc.
The script is deterministic in structure, creative in content
This gives you reproducibility where it matters (schema = your ground truth) and variety where it matters (prompt content = realistic inputs).
